## Чек-лист для сверки фронтенда

Это задачи на **проверку/интеграцию**, а не утверждение, что соответствующие элементы отсутствуют на сайте.

### 1. Конструктор опросов

- [ ] Позволяет выбирать `single_choice`, `multiple_choice`, `text`.
- [ ] Для `text` позволяет выбрать `textPurpose: feedback` или `knowledge`.
- [ ] Для `knowledge` показывает поля эталонного ответа, критериев и максимального балла (`knowledgeSettings`), не передаёт их в публичный интерфейс.
- [ ] Позволяет выбрать анонимный или именной режим до публикации; после публикации режим не редактируется.
- [ ] Корректно отображает ошибки `400` и конфликты статуса `409`.

### 2. Прохождение опросов

- [ ] Рендерит radio, checkbox или поле ввода текста согласно `type`.
- [ ] Для `identified` просит имя участника; для `anonymous` **не отправляет** `respondentName`.
- [ ] Перед отправкой инициализирует публичную сессию через `GET /api/public/polls/{id}`.
- [ ] При голосовании передаёт `X-AnonPulse-Vote: 1` и cookies (`credentials: include` в подходящей same-site конфигурации).
- [ ] Не предлагает повторное голосование после успешной отправки; учитывает `409`.

### 3. Результаты после закрытия

- [ ] Показывает сводную статистику и количество текстовых ответов.
- [ ] Даёт преподавателю возможность просматривать текстовые ответы.
- [ ] Для именных опросов показывает связанные ответы участников через защищённый endpoint.
- [ ] Не раскрывает индивидуальные данные участникам публичного опроса.

### 4. ИИ-анализ обратной связи

**Полный контракт и JSON-примеры уже находятся в [frontend-feedback-analysis.md](frontend-feedback-analysis.md).**

- [ ] Кнопка «Проанализировать отзывы» отображается только для закрытого опроса и вопроса `textPurpose: feedback`.
- [ ] Перед запуском преподавателю сообщается о передаче текстов GroqCloud и запрашивается явное подтверждение.
- [ ] `POST /api/polls/{pollId}/questions/{questionId}/feedback-analysis`: тело `{ "externalProcessingConfirmed": true }`, заголовок `X-CSRF-TOKEN`.
- [ ] `GET` того же адреса опрашивается только при `pending`/`processing`; при `completed` показывает `summary`, `themes`, `recommendations`, `limitations`.
- [ ] Для `failed` доступен **только ручной** повтор, для `429` соблюдается `Retry-After`.
- [ ] Не выполняются лишние повторные POST и не раскрывается отчёт публичным участникам.

## Важные замечания по безопасности

- ИИ-проверка знаний пока не реализована, даже если интерфейс позволяет создать вопрос `knowledge`.
- ИИ-анализ — действие преподавателя; тексты передаются внешнему провайдеру, а очистка email/телефонов не гарантирует абсолютную анонимность.
- Не копировать секреты API, cookie и приватные настройки вопроса в браузерный код или логи.
- Для state-changing API, защищённых CSRF, использовать `GET /api/auth/csrf-token` и заголовок `X-CSRF-TOKEN` в соответствующих запросах. Не предполагать, что CSRF нужен всем POST: ориентироваться на контракт endpoint.
- Пользовательские cookies имеют `HttpOnly`, `Secure`, `SameSite=Strict`. Сверять сетевую топологию frontend/backend и не пытаться читать cookie в JavaScript.

## Минимальные сценарии приёмки

1. **Анонимная обратная связь:** преподаватель создаёт опрос с `textPurpose: feedback`, публикует; участники оставляют тексты; преподаватель закрывает, видит ответы, запускает ИИ с подтверждением и получает `completed` с отчётом.
2. **Именной опрос:** преподаватель создаёт `responseMode: identified`, участник вводит отображаемое имя, после закрытия преподаватель получает именные отправки. Имя самодекларируемое, не подтверждённая личность.
3. **Проверка знаний без ИИ:** создать `textPurpose: knowledge`, вручную оценить ответы, финализировать попытку и получить личный результат по сохранённому `accessSecret`.

При изменениях API обновлять соответствующий документ из списка выше и, при необходимости, этот обзор.
