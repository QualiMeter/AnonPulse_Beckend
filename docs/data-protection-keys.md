# ASP.NET Core Data Protection Keys

AnonPulse хранит key ring ASP.NET Core Data Protection в существующей PostgreSQL-базе, в таблице `data_protection_keys`. Все экземпляры приложения используют одинаковое имя приложения `AnonPulse`, поэтому cookie-сессии могут переживать deployment и обслуживаться несколькими репликами при подключении к одной базе.

Миграция должна применяться до запуска версии приложения с этой настройкой. API не вызывает `Database.Migrate()` или `EnsureCreated()` автоматически.

## Применение миграции перед deployment

В репозитории хранится идемпотентный скрипт
`scripts/migrations/20261011212234_add_data_protection_keys.sql`. Он выполняется в
транзакции, проверяет `__EFMigrationsHistory`, создаёт только таблицу ключей и
регистрирует миграцию `20261011212234_AddDataProtectionKeys`.

Перед deployment сделайте backup базы, проверьте целевую строку подключения и
выполните скрипт от роли, которой разрешены `CREATE TABLE` и запись в
`__EFMigrationsHistory`:

```bash
psql "$DATABASE_URL" --set ON_ERROR_STOP=on \
  --file scripts/migrations/20261011212234_add_data_protection_keys.sql
```

После выполнения убедитесь, что миграция зарегистрирована:

```sql
SELECT "MigrationId"
FROM "__EFMigrationsHistory"
WHERE "MigrationId" = '20261011212234_AddDataProtectionKeys';
```

Не запускайте новую версию приложения до успешного завершения скрипта. Команда
не входит в startup контейнера и не подключается к production автоматически.

## Что защищает это изменение

- ключи не теряются при пересоздании контейнера;
- новые экземпляры приложения могут расшифровать cookie и другие payload, созданные предыдущим экземпляром;
- несколько реплик с одной базой используют общий key ring.

`SetApplicationName("AnonPulse")` изолирует payload AnonPulse от приложений с другим discriminator, но не шифрует строки ключей в базе.

## Ограничения хранения в PostgreSQL

По умолчанию XML в колонке `xml` содержит ключевой материал без дополнительной защиты на уровне приложения. Компрометация учётной записи БД, SQL dump, backup или доступа администратора PostgreSQL может раскрыть key ring. Обладающий ключами злоумышленник потенциально может создавать или читать защищённые ASP.NET Core payload, включая authentication cookie, пока соответствующие ключи действительны.

Минимальные эксплуатационные меры:

- отдельная роль PostgreSQL для приложения с минимальными правами;
- TLS для соединения с PostgreSQL;
- ограничение доступа к Railway project, переменным, backup и database console;
- шифрование дисков и backup средствами провайдера;
- аудит доступа, ротация credentials и план отзыва key ring после инцидента.

Шифрование storage или backup защищает носитель, но не защищает ключи от пользователя БД, способного выполнить `SELECT`.

## Варианты шифрования ключей в покое

1. Настроить `ProtectKeysWithCertificate` и хранить приватный ключ сертификата отдельно от PostgreSQL — например, в защищённом secret store или подключаемом read-only volume. Нужны резервирование сертификата и процедура ротации без потери старого сертификата до истечения всех зависимых payload.
2. Реализовать или подключить `IXmlEncryptor`/`IXmlDecryptor`, использующий внешний KMS/HSM. В PostgreSQL тогда сохраняется зашифрованный XML, а master key остаётся вне базы.
3. Использовать управляемое внешнее хранилище key ring с envelope encryption, если оно доступно в выбранной инфраструктуре.

Конкретный механизм нельзя включать без согласованного места хранения master key, политики ротации и процедуры восстановления. До этого PostgreSQL persistence обеспечивает долговечность и совместное использование ключей, но не дополнительное шифрование key material на уровне приложения.
